# PaySim Data Dictionary

## Scope and provenance

This dictionary separates three kinds of information:

- **Official dataset fact:** stated by the PaySim authors or the Kaggle dataset documentation.
- **Project observation:** calculated from the local file `PS_20174392719_1491204439457_log.csv`.
- **Modelling constraint:** a project rule adopted to prevent leakage or simulator-specific memorisation.

Official sources:

- [Kaggle: Synthetic Financial Datasets for Fraud Detection](https://www.kaggle.com/datasets/ealaxi/paysim1/data)
- [Lopez-Rojas, Elmir and Axelsson (2016), PaySim: A Financial Mobile Money Simulator for Fraud Detection](https://www.msc-les.org/proceedings/emss/2016/EMSS2016_249.pdf)

The Kaggle documentation states that this synthetic dataset represents one month of mobile-money activity and that one `step` equals one hour. It also warns that detected fraud transactions are cancelled. Therefore, all four balance columns must not be used for fraud detection.

## Column definitions

| Column | Observed type | Official meaning | Example | Project role | Modelling status |
| --- | --- | --- | --- | --- | --- |
| `step` | integer | One simulated hour. | `1` | Time attribute | **Restricted candidate.** Retain for chronological analysis and later validation, but test carefully because the local file has strong end-of-simulation fraud artifacts. |
| `type` | text | Transaction type: `CASH_IN`, `CASH_OUT`, `DEBIT`, `PAYMENT`, or `TRANSFER`. | `TRANSFER` | Transaction attribute | Candidate categorical feature. |
| `amount` | decimal | Transaction amount in local currency. | `181.00` | Transaction attribute | Candidate numeric feature. |
| `nameOrig` | text | Customer who initiated the transaction. | `C1305486145` | Origin identifier | Do not use as a raw predictive feature. Almost every origin appears once, creating high-cardinality memorisation risk. |
| `oldbalanceOrg` | decimal | Origin balance before the transaction. | `181.00` | Balance attribute | **ANALYSIS ONLY — PROHIBITED AS A PREDICTIVE FEATURE.** The official documentation excludes all balance fields because fraud transactions are cancelled. |
| `newbalanceOrig` | decimal | Origin balance after the transaction. | `0.00` | Post-transaction balance | **ANALYSIS ONLY — PROHIBITED AS A PREDICTIVE FEATURE.** It is post-transaction information and exhibits severe target leakage. |
| `nameDest` | text | Recipient identifier. `M` prefixes identify merchants whose balances are not recorded. | `C553264065` | Destination identifier | Do not use as a raw predictive feature. Repeated destinations can be memorised across random data splits. |
| `oldbalanceDest` | decimal | Recipient balance before the transaction. Merchant balances are unavailable. | `0.00` | Balance attribute | **ANALYSIS ONLY — PROHIBITED AS A PREDICTIVE FEATURE.** The official documentation excludes all balance fields because fraud transactions are cancelled. |
| `newbalanceDest` | decimal | Recipient balance after the transaction. Merchant balances are unavailable. | `0.00` | Post-transaction balance | **ANALYSIS ONLY — PROHIBITED AS A PREDICTIVE FEATURE.** It is post-transaction information and exhibits simulator artifacts. |
| `isFraud` | integer | Label for transactions generated by fraudulent agents. | `1` | Prediction target | Target only. Never use as an input feature. |
| `isFlaggedFraud` | integer | Existing rule flag for transfers greater than 200,000 in a single transaction. | `0` | Existing control output | Exclude from independent fraud prediction. It is another detector's decision, not a raw transaction characteristic. |

## Observed schema and quality

These are project observations from the local CSV, not official definitions:

- Shape: 6,362,620 rows and 11 columns.
- Step range: 1 through 743.
- No missing values in any column.
- `isFraud` and `isFlaggedFraud` contain only `0` and `1`.
- Every `nameOrig` begins with `C`.
- `nameDest` begins with either `C` or `M`; no other prefixes occur.

## Analysis-only balance derivations

The exploration calculates balance discrepancies solely to demonstrate leakage:

```text
expected origin after CASH_IN = oldbalanceOrg + amount
expected origin otherwise     = oldbalanceOrg - amount

expected customer destination after CASH_IN = oldbalanceDest - amount
expected customer destination otherwise     = oldbalanceDest + amount
```

Any difference between an expected value and a recorded new balance is also **analysis only and prohibited as a predictive feature**. This prohibition applies to every raw or derived value involving:

- `oldbalanceOrg`
- `newbalanceOrig`
- `oldbalanceDest`
- `newbalanceDest`
